# MCP, parte 1: plano de implementação (PR 5)

> **Para agentes:** sub-skill obrigatória: superpowers:subagent-driven-development (recomendada) ou
> superpowers:executing-plans, tarefa por tarefa. Os passos usam checkbox (`- [ ]`).

**Objetivo:** um agente de IA (ex.: o bot de dados do Kids, o Claude do dono) conecta na loja por um token e usa, como
ferramentas MCP, todas as ações não sensíveis que o papel do token permite, sem nunca receber dado pessoal do
comprador.

**Arquitetura:**
- Tabela `mcp_token` (com `store_id` e RLS). O token tem o formato `fnl_<storeId sem hífens>_<segredo>`: o servidor
  tira a loja do próprio token, abre a transação da loja e procura o sha256 do token, sem consulta fora do RLS.
- Ator novo `{ kind: "token", tokenId, role }`, aceito por `authorize` como um usuário com aquele papel. Papel novo
  `reader` (só para tokens). Origem `mcp` na auditoria, com o `tokenId`.
- Catálogo de ferramentas por lista branca (`src/lib/mcp/tools.ts`): cada ação exposta tem uma projeção de saída que
  mascara ou remove dado do comprador; ações sensíveis, públicas, de sistema e as excluídas pela spec não entram. Um
  teste falha se uma ação registrada não estiver classificada.
- Rota `POST/GET/DELETE /api/mcp` com o SDK oficial (`WebStandardStreamableHTTPServerTransport`, sem sessão, resposta
  JSON), um servidor por requisição com as ferramentas do papel do token.
- Ferramenta nova `orders.paidReport` (pedidos pagos por período, sem dado pessoal, paginada) e painel de tokens.

**Stack:** Next 16 (rota em Node), Drizzle e Postgres 17 (RLS), Zod 4 (`z.toJSONSchema`), SDK MCP oficial, testes em
Bun.

**Spec:** `docs/superpowers/specs/2026-11-20-kids-migracao-design.md` (seção "4. MCP" e "O que seria fracasso").

## Restrições globais

- **Nenhum dado pessoal do comprador sai pelo MCP, em nenhum papel.** Nome, e-mail, telefone e CPF do comprador saem
  mascarados ou não saem; busca por e-mail/nome (`q` de `orders.list`) não é exposta; `orders.export` fica fora; IP,
  user agent, `fbc`, `fbp` e e-mails de equipe que aparecem em histórico também não saem.
  - Máscaras: e-mail `m***@gmail.com` (primeira letra + `***` + domínio); nome `M***` (primeira letra);
    telefone `(**) *****-1234` (só os 4 últimos dígitos); CPF `***.***.***-12` (já existe `maskCpf`).
- **Ações sensíveis não aparecem pelo MCP neste PR** (a fila de aprovação é o PR 6). Continuam bloqueadas também no
  `runAction` (`approval_required`).
- **Decisões novas desta etapa:**
  - `connections.removeTelegram` passa a ser **sensível** (um agente não desliga os avisos da loja sem aprovação);
  - `connections.testSmtp`, `connections.testResend` e `connections.testTelegram` ficam **fora do MCP** neste PR
    (enviam mensagem a endereço escolhido por quem chama; voltam na revisão da matriz do PR 6);
  - `products.create` fica fora (recebe o arquivo; o upload por link é o PR 6).
- **Token:** `fnl_` + `storeId` (32 hex, sem hífens) + `_` + 32 bytes aleatórios em base64url (43 caracteres). Só o
  sha256 é guardado; o painel mostra o token **uma vez**. Na lista aparecem nome, papel, `fnl_…` + os 4 últimos
  caracteres, criado em, criado por, último uso e revogado em. `last_used_at` é atualizado no máximo 1 vez por minuto.
  Nenhum literal com o formato do token nos testes (monte em tempo de execução).
- **Papéis do token:** `owner`, `admin`, `support`, `traffic`, `reader`. `reader` tem só `products.read`,
  `offers.read`, `metrics.read` e `orders.report`. Tokens são criados e revogados por quem tem `team.manage` (as ações
  de token são sensíveis, então não saem pelo MCP).
- **Permissão nova `orders.report`** (para `orders.paidReport`): todos os papéis que têm `metrics.read` ou
  `orders.read` (owner, admin, support, traffic, reader).
- **Endpoint:** `Authorization: Bearer <token>`; sem token, malformado, revogado ou desconhecido → HTTP 401 com corpo
  JSON-RPC de erro fixo (sem dizer qual caso); corpo até 256 KB (413); limite de 120 requisições por minuto por token
  (429). Nome das ferramentas: o nome da ação com `.` trocado por `_` (ex.: `orders_paidReport`), para caber em
  `^[a-zA-Z0-9_-]{1,64}$`.
- **Erros das ferramentas:** `ActionError` vira resultado de ferramenta com `isError: true` e texto
  `<código>: <mensagem>` (a mensagem das ações já é segura); qualquer outro erro vira `error: falha interna` e vai para
  o log só com o código. Nunca pilha.
- **Regras do repo:** rotas só chamam `runAction`; toda tabela nova com `store_id` + `enable_store_rls`; sem APIs
  exclusivas do Bun em `src/`; dependência nova com versão exata publicada há pelo menos 2 semanas.
- **Escopo do PR:** produto. Não edita `e2e/`, `scripts/verify*`, `.github/`, `.claude/`, `REVIEW.md`.
- **Processo:** `bun run check` antes de cada commit e `bash scripts/verify.sh` antes do PR.

## Foco de revisão

1. **PII por qualquer ferramenta:** com um pedido semeado com nome, e-mail, telefone, CPF, IP e user agent distintos,
   chamar **todas** as ferramentas expostas (com entrada mínima válida) pelo endpoint, com token `owner`, e conferir
   que nenhuma resposta contém esses valores. Teste na Task 4.
2. **Ação nova sem classificação:** uma ação registrada que não está nem na lista branca nem na lista de excluídas faz
   um teste falhar (quem criar ação nova decide se ela sai pelo MCP). Teste na Task 3.
3. **Token de outra loja ou forjado:** token com o `storeId` da loja A e o segredo de um token da loja B; token
   revogado; token com `storeId` inexistente; tudo → 401 igual. Testes nas Tasks 1 e 4.
4. **Papel do token:** token `reader` não lista nem chama `orders_list`; token `traffic` não chama ação de
   `connections.write`. Testes nas Tasks 3 e 4.
5. **Auditoria:** ação feita pelo MCP grava `origin: "mcp"` e o `tokenId` no ator. Teste na Task 4.
